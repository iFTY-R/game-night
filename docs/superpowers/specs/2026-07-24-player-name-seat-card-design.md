# 玩家用户名与桌沿席签设计

## 1. 范围

本次变更统一解决两项直接相关的问题：玩家用户名过长导致桌面席位持续截断，以及共享玩家卡片像悬浮信息条、没有贴合游戏桌。开发环境现有玩家与游戏数据不保留，规则不需要兼容历史长用户名。

不改变设备指纹登录、管理员登录、房间成员身份、游戏规则、座位顺序和实时投影协议。

## 2. 用户名规则

用户名在 NFKC 规范化并去除首尾空白后，必须同时满足：

- 长度为 2 到 4 个 Unicode code point，边界均包含。
- 每个 code point 只能是 Unicode Han 字母、Unicode Latin 字母，或 Unicode General Category=`Nd` 的十进制数字。`Nd` 数字按数字类别放行，不因其所属书写系统被额外拒绝。
- 不允许内部空白、下划线、标点、Emoji、控制字符、格式字符，以及 Han/Latin 以外的其它字母类文字系统。
- `2-4` 上限只作用于 NFKC 并去除首尾空白后的 display code point 数；case-fold 后的唯一键允许扩展，不重复执行 `2-4` 长度校验。
- 规范化结果继续执行大小写折叠唯一键、保留名和敏感片段校验。保留名与敏感片段使用独立的 folded-key 规范化，不受公开用户名 `2-4` code point 长度上限限制；例如 `admin`、`administrator` 等超长保留词仍可配置并生效。
- API/领域值对象是最终权威；浏览器输入限制只负责提前反馈，不能代替服务端校验。
- 用户名不再要求全局唯一。不同用户可以持有相同的规范化用户名；身份恢复、设备凭据和后台配置继续以恢复码、设备凭据和 `user_id` 为主，不依赖用户名唯一性。
- 房间展示名以 `room_members.display_username` 为房间内可见真值，并同步保存对应的 `username_key`。同一房间内对 `NFKC + trim + case-fold` 后的唯一键执行排重；不同房间允许重名。
- 加入房间时如果房间内已有同名唯一键，加入必须失败并返回稳定业务错误 `room.username.taken`；用户改名时如果任一所在房间发生冲突，整次改名事务必须回滚，不允许部分房间先更新。
- 并发加入、并发改名和重试场景以下层数据库唯一约束为最终权威。前端预检查与服务层查询只负责提前反馈，不能替代 `(room_id, username_key)` 唯一约束和事务回滚。

首次设置用户名时，界面明确显示“2-4 个汉字、英文字母或数字”，输入超界或含非法字符时不能提交。错误提示不能回显服务端私密策略内容。

## 3. 桌沿席签

共享 `PlayerSeat` 采用固定稳定的横向席签结构：头像、玩家名、短状态。玩家名在新规则下默认完整显示；组件仍保留省略和可访问名称，防止异常或外部数据撑破布局。

席签通过一个短连接脚与桌沿发生视觉连接，避免像悬浮工具卡。状态层级如下：

- 普通玩家：中性边框、完整昵称、一个短状态。
- 当前行动玩家：金色边框和席签外部的紧凑行动标记；本地玩家显示“轮到你”，其他玩家显示“行动中”。
- 本地玩家：使用轻量“你”标识，不依赖高亮色表达行动状态。
- 房主：使用皇冠图标，不占用用户名的可用宽度。
- 断线玩家：降低对比度并显示断线图标，但保持姓名可读。

以上状态可叠加，不是互斥枚举：同一席签可同时具备 `self`、`active`、`host`、`offline`；短状态文案继续显示业务状态，不被“轮到你”或“行动中”替代。

普通席位与当前席位使用同一组件和基本几何，当前席位只允许轻微增强，不形成与其它玩家割裂的另一套卡片。连接脚不能增加交互命中区，席签本身不新增点击行为。

## 4. 响应式约束

- 在 2 人、4 人和当前支持的最大多人布局下，竖屏 360x640、390x844 和横屏 844x390 中席签不能超出游戏桌容器或覆盖中心回合信息。
- 座位尺寸必须通过 `GameTable` 的布局参数与 CSS 变量保持一致，不能只放大视觉宽度而继续用旧碰撞尺寸。
- 多人布局继续以自己的座位为底部锚点，操作托盘展开、折叠时不改变席签尺寸。
- 动画遵守 `prefers-reduced-motion`，状态变化不能造成布局跳动。

## 5. 开发数据重置

实现与验证完成后，仅清空开发数据库中的非管理员身份及游戏运行数据，包括玩家身份、设备与恢复凭据、用户名声明、个人资料、房间成员、房间、游戏会话、事件、计时器、回放授权、实时租约、游戏 inbox 和操作回执。

保留数据库 schema、Goose 迁移记录、开发 keyring、激活管理员账户及维持其安全状态所需的管理员和审计数据。不得删除或重写 `admin_accounts`、`admin_sessions`、`admin_challenges`、`admin_totp_enrollments`、`admin_recovery_codes`、`admin_assisted_recovery_grants`、`audit_chain_head`、`audit_events`，以及 `audit.checkpoint` 或管理员重置相关的 outbox 记录。重置必须在 API、Realtime 和 Worker 停止后执行；完成后重启全部服务并重新检查 readiness。

## 6. 验收标准

1. `ab`、`玩家`、`A9界2` 和 NFKC 后合法的 2-4 字符用户名可通过领域解析。
2. 1 字符、5 字符、空白、下划线、标点、Emoji、控制/格式字符和非汉字/拉丁文字系统被拒绝。
3. 首次用户名表单在输入过程中按与领域一致的 `NFKC + trim` 结果校验，并显示统一提示“2-4 个汉字、英文字母或数字”；对 1 字符、5 字符、内部空白、下划线、标点、Emoji、控制/格式字符和非法文字系统给出即时反馈。非法值不得发起 `CompleteOnboarding` RPC，合法值可完成 onboarding。
4. 不同用户允许全局重名；同一房间内对 `NFKC + trim + case-fold` 后的唯一键执行排重。加入房间和改名都必须遵守该规则；同房间冲突返回稳定业务错误 `room.username.taken`，改名冲突时事务整体回滚。
5. 并发加入或并发改名时，数据库唯一约束是最终权威；即使多个请求同时通过前置检查，最终也只能有一个请求成功写入该房间唯一键。
6. 组件测试覆盖普通、self、active(remote)、active(self)、host、offline，以及至少两个叠加组合（`self+active+host`、`host+offline`）；用户名区域宽度不因状态图标缩窄，业务状态文案与行动标记同时存在。
7. 在 2 人、4 人和当前支持的最大多人布局下，分别对 `360x640`、`390x844`、`844x390` 做视觉检查；当 `selfSeatIndex` 非 0 时，本地席位仍锚定底部，席签不遮挡中心回合信息或私有操作区。组件测试同时断言 `GameTable` 传入的 seat 尺寸与 `--gn-seat-width`、`--gn-seat-height` 保持一致。
8. 开发数据重置后没有旧玩家、房间或游戏会话；API、Realtime、Worker 和 Web 全部恢复健康。
