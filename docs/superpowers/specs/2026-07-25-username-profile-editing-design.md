# 用户资料入口与房间重名改名设计

## 1. 范围

本次变更为设备身份增加可发现的用户名修改入口，并补齐加入房间时遇到同名玩家的恢复流程。用户仍通过设备凭据自动登录，首次进入系统仍必须先设置用户名；本次不增加密码、手机号、头像上传、独立个人中心或游戏进行中的资料操作。

变更覆盖 Web 首页、房间等候与赛后页面、身份客户端与状态仓库、用户名领域规则、PostgreSQL 乐观并发写入，以及对应自动化测试。头像入口只落在 `HomeView`，以及 `RoomView` 的 lobby/post-game 状态；`RoomView` 的 playing 状态、所有游戏会话页面和 `ReplaySessionView` 都不增加资料入口，避免干扰进行中对局和复盘。

## 2. 用户名修改规则

- 用户主动修改用户名不再受 30 天冷却限制。领域模型、持久化 CAS 查询和错误映射中删除只为该冷却服务的约束；无需新增例外凭证或房间专用改名接口。
- 身份写接口现有的设备认证、Origin、双提交 CSRF、请求限流和事务边界继续生效。取消时间冷却不等于取消滥用防护。
- 用户名继续执行 `NFKC + trim`，且必须是 2 到 4 个汉字、拉丁字母或十进制数字。保留名、敏感片段和服务端策略仍由 API 最终裁决。
- 新用户名的规范化唯一键与当前用户名相同时不能提交；大小写或兼容字符归一后没有实际变化也视为未修改。
- 用户名仍不要求全局唯一。不同用户可以使用相同名字，但同一房间内必须唯一。
- 修改用户名时，所有该用户仍加入的房间都必须满足房间内唯一性。任一房间冲突时，身份用户、用户名声明和所有房间成员展示名全部回滚，并返回稳定业务键 `room.username.taken`。
- 旧用户名的现有按用户保留记录继续保留，不改变管理员强制改名和审计语义。
- PostgreSQL 写入继续比较旧用户名、旧更新时间和旧 `username_changed_at`，防止并发改名覆盖；仅移除时间截止条件，不弱化 CAS。

## 3. 资料入口

新增共享 `ProfileTrigger`：

- 使用稳定的圆形按钮，显示当前规范化用户名的第一个 Unicode code point。当前合法字符集不含组合 Emoji，因此无需额外引入字素切分依赖。
- 按钮的可访问名称和 `title` 包含完整用户名与“修改用户名”意图，键盘可聚焦，命中区域不小于 40px。
- 首页身份已激活时，使用该按钮替换当前“设备已识别”文字徽标；尚未完成首次设置时继续显示“设备登录”。
- `RoomView` 仅在 lobby/post-game 状态将按钮放在顶栏右侧，与人数信息组成稳定操作组；playing 状态隐藏该按钮。游戏会话路由和独立复盘路由不渲染该入口。

新增共享 `UsernameDialog`：

- 移动端表现为贴近屏幕底部的紧凑弹层，桌面端为居中弹层；使用同一组件和同一表单，不维护两套交互。
- 弹层展示当前用户名、用户名输入、统一规则提示、取消和确认操作。打开时预填当前值并聚焦输入；关闭时清空错误、提交状态和冲突上下文。
- 点击遮罩、按 Escape 或取消按钮走同一关闭流程。提交期间禁止重复提交和意外关闭。
- 输入无效、与当前用户名归一后相同或请求进行中时，确认按钮禁用。服务端错误在弹层内显示，不使用全局通知替代。
- 普通入口的确认文案为“保存用户名”；为解决进房重名而打开时，标题说明房间内已有同名玩家，确认文案为“改名并进房”。

## 4. 客户端状态与错误契约

- `identityClient` 增加 `ChangeUsername` 调用，继续复用现有同源 Connect JSON、设备 Cookie、CSRF 和请求 ID 机制。
- `ApiError` 除 HTTP 状态、Connect code 和本地化展示文案外，新增只读的原始业务键。解析错误时优先从 Connect details 中类型为 `platform.common.v1.BusinessErrorDetail` 的详情读取 `messageKey`；只有旧响应缺少该详情时，才允许把符合业务键格式的原始 `message` 作为兼容回退。展示文案再由业务键本地化，不能通过比较中文文案识别业务分支。
- `room` store 增加改名 action。它先执行浏览器侧格式校验，再调用服务端；成功后用响应中的权威 `userId`、`status` 和 `username` 更新 Pinia，并立即持久化 localStorage。
- 改名成功后刷新“我的房间”和“公开房间”。如果用户当前位于房间页，还要重新获取当前房间快照，使所有成员位置上的自己、房主名称和房间列表文案使用同一权威用户名。
- 刷新列表中的单个失败不能撤销已成功的用户名修改。界面保留新用户名，并以非阻断提示告知列表可稍后刷新；当前房间快照刷新失败时保留服务端改名成功结果，但显示同步失败提示。

## 5. 房间重名恢复流程

所有能发起加入的入口都使用同一冲突处理：房间码表单、邀请链接和公开房间列表。

1. 页面记录本次加入目标和加入意图，然后发起正常加入请求。
2. 请求失败且 `ApiError.businessKey === "room.username.taken"` 时，不清除输入、不跳转，也不把该错误当成普通失败；页面显示“房间内已有同名玩家”和“修改用户名后重试”按钮。
3. 用户点击按钮后，以冲突模式打开共享改名弹层。用户仍可以取消并留在当前页面。
4. 改名成功后，页面只自动重试一次原加入动作。重试成功则采用返回的房间 ID 与房间码、保存权威快照并按原流程进入房间。
5. 自动重试若因其它原因失败，显示对应错误并停止；如果仍返回重名，保留冲突操作供用户再次主动选择其它名字，不能递归自动打开或无限重试。
6. 用户从顶栏普通入口打开改名弹层时，不携带任何待加入动作，成功后只刷新身份相关页面状态。

待加入上下文只保存在首页组件生命周期内，不写入 localStorage 或 Pinia。刷新页面后，邀请链接本身仍能恢复目标房间；手输房间码和公开列表动作不需要跨刷新恢复。

## 6. 响应式与可访问性

- 头像按钮不得挤压品牌、房间码、分享按钮或人数信息。360px 竖屏下房间顶栏保留返回、房间码和头像；人数可使用现有紧凑布局，但不能与头像重叠。
- 弹层尊重移动端安全区，软键盘出现时输入与提交操作仍可见；内容高度超出视口时仅弹层内容滚动。
- 弹层具有对话框语义、标题关联、初始焦点、焦点回收和键盘关闭能力。错误区域使用 `role="alert"`，提交状态使用可访问的忙碌语义。
- 动效只用于弹层进入和退出，遵守 `prefers-reduced-motion`；头像本身不使用持续动画。
- 视觉颜色继续使用平台主题变量，圆形头像不引入游戏主题耦合，也不改变游戏桌主题接口。

## 7. 测试与验收标准

1. 活跃用户可在首次设置用户名后立即修改，不再产生 `identity.username.change_cooldown`；连续改名仍经过现有限流和每次写入的乐观并发检查。
2. 领域和持久化测试证明：无时间冷却、同名未变化被拒绝、并发旧快照不能覆盖新值、旧用户名记录继续保留、任一所在房间重名时整笔事务回滚。
3. API 客户端测试证明：包含 `BusinessErrorDetail` 时优先采用其中的 `messageKey`；缺少详情的旧响应可从原始 `message` 兼容回退；最终 `ApiError` 同时保留 `code="already_exists"`、`businessKey="room.username.taken"` 和本地化展示文案。现有设备失效本地化行为不回归。
4. store 测试覆盖合法改名请求、无效输入不发请求、服务端权威用户名写入 Pinia 与 localStorage，以及改名失败不污染本地身份。
5. 首页测试覆盖身份激活后显示首字头像、普通改名、房间码重名、邀请链接重名、公开房间重名、取消改名、成功后仅重试一次和二次失败停止。
6. 房间页测试覆盖 lobby/post-game 状态的头像位置、playing 状态和独立复盘页不显示头像、成功改名后刷新当前房间，以及其它房间重名导致改名失败时保留原快照和原用户名。
7. 同步恢复测试分别覆盖“我的房间”刷新失败、“公开房间”刷新失败和当前房间快照刷新失败。三种情况下都必须保留服务端已确认的新用户名及其本地持久化，只显示非阻断同步提示，不回退身份，也不重复提交改名请求。
8. 在 `360x740`、`390x844`、`844x390` 和桌面视口验证首页与房间页：顶栏无重叠、头像命中区稳定、底部弹层不被安全区或软键盘逻辑遮挡、桌面弹层不过宽。
9. Web 类型检查、相关 Vitest、Go 领域测试、PostgreSQL 集成测试和生产构建通过；不新增第三方依赖，不修改游戏进行页布局。
