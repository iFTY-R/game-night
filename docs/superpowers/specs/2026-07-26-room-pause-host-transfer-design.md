# 房间暂停与房主转移设计

## 1. 范围与语义

本次变更为持续房间增加完整的暂停治理与房主转移能力。暂停只作用于正在进行的游戏会话，不改变房间的 `playing` 状态，不结束本局，也不允许暂停期间继续提交游戏动作或触发计时器。

- 房主可以直接暂停和恢复当前游戏。
- 当前游戏的参与玩家可以发起暂停申请；旁观者不能申请暂停。
- 房主可以批准或拒绝当前待处理申请。批准后立即暂停，拒绝后清除申请。
- 同一房间同一时间最多存在一条待处理暂停申请。申请人不能重复申请，其他玩家看到已有申请后不能覆盖。
- 房主可以在 `lobby`、`playing` 和 `post_game` 状态把房主身份转移给当前仍在房间内的参与玩家；不能转给自己、旁观者、等待准入用户或已离开用户。
- 转移成功后旧房主立即失去房主权限，新房主立即继承准入、开局、暂停审批、恢复、踢人、切换游戏和继续转移等权限。
- 房间关闭、当前会话结束或取消时清除暂停申请和暂停展示状态。房间本身不能在没有活动会话时进入暂停状态。

本次不增加投票暂停、自动批准、定时自动恢复、暂停次数限制、房主离线自动转移或历史暂停审计页面。这些能力如后续需要，应建立在本次稳定的命令与事件边界上。

## 2. 架构方案

采用“房间治理状态 + 游戏会话运行状态”的双层方案：

- `platform/room` 是权限与治理权威，保存当前待处理申请和活动暂停信息，校验申请人、审批人、恢复人及房主转移目标。
- `platform/game-runtime` 是运行权威，通过现有 `active`/`suspended` 状态阻断动作、系统命令和计时器，并在恢复时平移所有未到期计时器。
- API 编排层在一个数据库事务中提交房间治理变化与会话生命周期变化。批准暂停、房主直接暂停和恢复都不能出现“房间显示暂停但会话仍可操作”或相反的半提交状态。
- Connect 协议暴露显式命令，不使用通用状态更新接口。每个写命令携带操作 ID、房间版本和成员版本；需要修改活动会话时同时校验会话 ID 与会话所有权栅栏。
- 房主转移继续使用现有 `ownership_epoch`。转移时房间版本和 `ownership_epoch` 同时递增，所有携带旧房主栅栏的并发治理写入都必须失败。

未采用的方案：

- 只修改前端状态：不能阻止服务端动作和计时器，不满足一致性要求。
- 只使用游戏会话 `suspended`：无法表达待审批申请、申请人和房主治理，也不能让房间快照独立恢复界面。
- 引入独立工作流服务：当前暂停只跨房间与单个活动会话，新增服务会扩大部署和事务复杂度，没有形成独立边界的收益。

## 3. 领域状态与业务规则

房间快照新增两个可选结构：

- `PendingPauseRequest`：申请 ID、申请人用户 ID、申请时间。只在 `playing` 且活动会话为 `active` 时有效。
- `ActivePause`：暂停 ID、发起来源 `host` 或 `approved_request`、申请人用户 ID（房主直接暂停时为空）、执行暂停的房主用户 ID、暂停时间。只在活动会话为 `suspended` 时有效。

领域命令及约束：

1. `RequestPause`：调用者必须是当前活动会话冻结参与者、仍是房间参与玩家且不是房主；房间必须正在游戏、会话未暂停、没有待处理申请。
2. `RejectPause`：只有当前房主可以执行；必须命中当前申请 ID，清除申请但不改变会话。
3. `Pause`：房主直接暂停时无需先创建申请；批准申请时必须命中申请 ID。两种路径都设置 `ActivePause`、清除待处理申请并把会话切换为 `suspended`。
4. `Resume`：只有当前房主可以执行；清除 `ActivePause` 并把同一活动会话切回 `active`。
5. `TransferHost`：只有当前房主可以执行；目标必须是当前参与玩家。变更 `HostUserID`，递增 `ownership_epoch` 和房间版本，不改变成员版本、座位、活动会话、准入设置、暂停状态或待处理申请。若待处理申请恰好由新房主发起，则清除该申请，因为新房主已能直接暂停。

所有命令都使用现有乐观并发版本和操作幂等机制。旧快照、重复审批、暂停后到达的申请、恢复后重放的恢复命令以及旧房主操作必须返回稳定业务错误，不静默覆盖新状态。

## 4. 计时冻结与实时一致性

暂停不能消耗玩家原本剩余的行动时间。会话暂停时记录规范化的 `suspended_at`；恢复时计算 `resume_at - suspended_at`，把所有持久化计时器的 `due_at` 及会话 `next_deadline_at` 整体向后平移相同持续时间，然后清空 `suspended_at`。

- 暂停期间计时器扫描仍只选择 `active` 会话，因此不会执行到期事件。
- 恢复与计时器平移必须在同一事务完成；恢复提交后才允许计时器工作器重新领取任务。
- 多次暂停分别累计各自的暂停时长，不修改游戏状态版本，也不重新调用游戏模块。
- 已在暂停事务提交前成功锁定并提交的动作或计时器结果可以生效；暂停事务使用版本和所有权 CAS，必须基于其后的最新快照提交。暂停提交成功后到达的动作统一返回“游戏已暂停”。
- 实时层继续以 PostgreSQL 为权威。房间与会话提交后发布更新通知；漏掉通知的客户端通过现有轮询和投影重新收敛。

会话投影增加暂停状态和暂停时间，但不向普通成员暴露内部所有权令牌。房间快照暴露待申请和活动暂停的必要展示字段，使刷新页面、断线重连和更换设备视图都能恢复正确界面。

## 5. 接口与持久化

房间服务新增显式 RPC：

- `RequestRoomPause`
- `RejectRoomPauseRequest`
- `PauseRoomGame`
- `ResumeRoomGame`
- `TransferRoomHost`

批准申请使用 `PauseRoomGame` 并携带待申请 ID；房主直接暂停不携带申请 ID，避免维护两套暂停实现。响应均返回最新房间；会话生命周期发生变化的命令同时返回最新投影或提供足够游标让客户端立即刷新。

PostgreSQL 的房间记录持久化待申请与活动暂停字段，游戏会话增加 `suspended_at`。生命周期 CAS 查询支持原子写入会话状态、暂停时间、平移后的计时器和 `next_deadline_at`。房主转移复用房间 CAS 更新 `host_user_id` 与 `ownership_epoch`，不新增第二套权限版本。

稳定业务错误至少覆盖：非参与玩家申请、申请已存在、申请不存在或已变化、会话已暂停、会话未暂停、无活动会话、仅房主可操作、无效转移目标和旧房主权限已失效。传输层映射到现有 `BusinessErrorDetail`，Web 依赖业务键而不是中文文案判断流程。

## 6. 移动端交互

暂停操作融入游戏桌现有操作托盘，不新增长期占据半屏的独立管理面板：

- 房主在进行中看到紧凑的暂停图标按钮；暂停后同一位置变为恢复按钮。两项高影响操作都使用确认弹层，防止误触。
- 非房主参与玩家看到“申请暂停”；提交后变为不可重复点击的“已申请”，并显示等待房主处理。旁观者不显示申请入口。
- 房主收到申请时，在桌面操作托盘上沿显示一条紧凑治理提示，可展开查看申请人，并执行“批准暂停”或“拒绝”。提示不遮挡桌面、玩家卡片或游戏关键状态。
- 暂停成功后，桌面保留完整游戏状态，在桌面中心显示克制的“游戏已暂停”状态层；所有游戏动作控件禁用。房主获得明确的恢复主操作，其他玩家只看到等待房主恢复。
- 暂停状态不关闭操作托盘，不切换路由，不重置玩家座位和当前行动高亮；持续动画和回合倒计时视觉停止，恢复后从冻结的剩余时间继续。

房主转移入口放在玩家信息弹层中。房主点击其他参与玩家的座位卡，查看信息后选择“转移房主”；二次确认明确显示目标用户名和“转移后立即失去房主权限”。不能转移的座位不显示该操作。成功后关闭弹层并用最新房间快照刷新全部房主标记和操作权限。

所有弹层复用项目现有对话框与表单约定。按钮命中区不小于 40px，禁用状态与原因可访问；`360x740`、`390x844` 和 `844x390` 下不得遮挡主要游戏内容。`prefers-reduced-motion` 下暂停过渡不使用持续动画。

## 7. 测试与验收标准

1. 房主可在活动会话中直接暂停和恢复；非房主不能调用房主命令，旧房主在转移完成后立即失去权限。
2. 当前参与玩家可申请暂停；旁观者、已离开成员、房主、重复申请者及并发第二申请均被稳定拒绝。房主可批准或拒绝精确的当前申请。
3. 批准申请或直接暂停后，动作、系统命令和计时器均不能推进状态；恢复后可以继续，游戏状态版本在纯暂停/恢复过程中不增加。
4. 一个剩余 20 秒的计时器暂停 30 秒后恢复，新的到期时间仍保留约 20 秒；多次暂停累计正确，`next_deadline_at` 与所有计时器一致。
5. 暂停、恢复、批准与房主转移的数据库写入具备原子性和 CAS 保护；故障注入不能产生房间治理状态与会话状态不一致。
6. 刷新页面、断线重连和漏掉实时通知后，客户端可从权威房间快照和会话投影恢复待申请、已暂停、当前房主和正确的剩余时间。
7. 房主转移保留座位、准入、游戏选择、活动会话和暂停状态；不能转给旁观者、等待用户、已离开用户或自己。新房主若是待申请人，该待申请被清除。
8. Web 测试覆盖房主暂停/恢复、成员申请、房主批准/拒绝、禁用动作、玩家信息弹层转移房主、并发错误恢复和移动端布局。
9. Go 领域测试、PostgreSQL 集成测试、Connect 契约测试、Web 类型检查、Vitest、生产构建和桌面 Playwright 视觉检查全部通过。
